# UI 文案规则

> 界面上的字是**给玩家看的**，不是给维护者看的。
> 这份文档定义什么不该出现在界面上，以及**怎么用机器拦住它**。

违反会由 `apps/web/src/ui-copy.test.ts` 直接判失败：

```bash
pnpm -C apps/web test src/ui-copy.test.ts
```

---

## 1. 三类红线

### ① 解释机制 / 解释一个玩家没问、也不存在的功能

| ❌ 反面例子 | 问题 |
|---|---|
| 「本地记录不会并入账户」 | 在解释一个**我们没做**的功能。玩家不知道有"历史迁移"这回事，是我们主动提起的 |
| 「两种模式抽到的是不同的颜色」 | 实现细节。玩家不需要知道种子怎么算 |
| 「每个身份每天一次；切换身份，就是切换到该身份对应的那一次」 | 背诵内部规则，而且这句话本身就是绕的 |

### ② 背诵禁令 / 免责声明

| ❌ 反面例子 | 问题 |
|---|---|
| 「刷新不变，不能重抽」 | 陈述事实就够了。主动列限制，等于假设玩家会去钻空子 |
| 「不能购买、不能追加」 | 同上。没说"能买"之前，没人会以为能买 |
| 「CP 只用于评分和稀有度，不是货币」 | **主动声明"这不是钱"，反而在暗示它是钱** |

### ③ 内部实现泄漏到界面上

| ❌ 反面例子 | 问题 |
|---|---|
| `localStorage` / `badgeIds` / `HistoryItem` | 存储与类型名 |
| 「本地模式」「登录模式」 | 内部模式名。玩家只关心**自己现在登没登录**，不关心我们把状态叫第几种模式 |
| `useDailyColor()` / `getDaily()` | 函数名 |
| `ep = 100 / p`、`2²⁴ 全色域枚举`、`fnv1a` | 算法细节属于 `docs/` |

## 2. 两个上下文，规则不同

| 页面 | 能放什么 |
|---|---|
| **操作页**（首页 `/`、登录 `/login`、我的 `/me`、图鉴 `/badges`） | 只放**操作需要的信息与状态**。不解释机制、不背诵规则、不做免责 |
| **关于页** `/about` | 它本来就是用来解释玩法的，**可以**讲规则与算法——但同样不背诵禁令、不说「不是 X」 |

判断方法：**玩家读到这句话，会不会产生一个原本没有的疑问？**
会 → 删掉。比如「不会并入账户」，玩家本来根本没想过"并入账户"这回事。

## 3. 怎么写才对人友好

| 想说的 | ❌ 别这么写 | ✅ 这么写 |
|---|---|---|
| 今天还没抽 | 「每天 UTC 00:00 重置，刷新不变，不能重抽。」 | 「每天 00:00 UTC 换新色。」 |
| 另一枚徽章没加分 | 「被同组更强牌型取代，不计分（同一条规则的不同强度档位只取最高分）」 | 区块标题「同类更强」+ 悬停提示 |
| 没命中任何徽章 | 「这个颜色一条徽章都没命中——也算一种稀有。」 | 「没有命中任何徽章。」 |
| 登录有什么好处 | 「登录后使用账户身份的每日颜色，历史记录**保存在服务端**，跨设备一致。」 | 「登录后，颜色和历史在任何设备上都能看到。」 |
| 本地模式的状态 | 「记录**只保存在这台设备上**，登录后历史会**保存在服务端**、跨设备一致。」 | 「登录后，颜色和历史在任何设备上都能看到。」 |
| 稀有度怎么定的 | 「由分数在全部 1677 万种颜色中的位置决定」 | 保留——这是**事实**，不是机制解释，玩家会觉得有意思 |

**注意最后两行是同一件事**：先说「存在服务端」，再说「不并入账户」，都是在回答玩家没问的问题。
真正有用的信息只有一条——**换设备还看不看得到**。说这个就够了。

**允许**：陈述玩家会观察到的事实、给操作反馈、说清楚去哪里点。
**不允许**：解释为什么会这样、列出限制、把内部名词搬出来。

## 4. 维护者视角 vs 玩家视角

`<script>` 里的注释**应该**讨论机制——那是写给维护者的，不受本规则约束。
`<template>` 里渲染的文字才受约束。

同理，开发者的 TODO **不要**渲染出来；写成注释，页面留空态或"还在开发中"。

## 5. 加新规则

在 `apps/web/src/ui-copy.test.ts` 的 `FORBIDDEN` 数组里加一条：

```ts
[/你的正则/, '给未来的自己解释为什么要拦它'],
```

**加完请做一次变异验证**：临时把违规文案塞进任意 `.vue`，确认测试真的变红，再还原。
没红过的测试等于没有测试。

## 6. 已知覆盖边界

- 只扫 `.vue` 的 `<template>`，**不扫** `.ts` 里拼出来的文案（如 composable 的错误提示）。
  那些目前都是「读取失败，请稍后重试」这类安全措辞，暂时不需要约束。
- 正则只能拦**已知措辞**，拦不住**新写的**。加红线是滞后的：
  每次改完界面，**把页面实际渲染的文字拉出来读一遍**（`document.body.innerText`），
  比只看正则可靠。发现新的坏措辞就补进 `FORBIDDEN`，并做一次变异验证。
- 模板里的 `<!-- 注释 -->` 会被剥掉后再检查，`<script>` 注释根本不扫——
  这两处都可以正常讨论机制与模式名。
- 正则也拦不住**语气**。措辞干净但居高临下的句子，仍然要靠人看。
