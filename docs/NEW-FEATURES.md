## 1. 功能① 徽章详情

### 1.1 玩家看到什么 / 做什么

在图鉴 `/badges` 点任意一条徽章（已获得或未获得都行），条目**就地展开**，
看到它的真实概率、判定条件、以及**自己哪几天命中过它**。再点一次收起。

### 1.2 交互流程

```
/badges
  └─ 家族分组 ── 徽章条目（现状：li，已获得完整展示 / 未获得只显示名称）
       │
       └─ 点击条目 ── 就地展开徽章详情（li 内部多一段 <div>）
            ├─ 真实概率（大字）
            ├─ 判定条件（未获得时不显示，沿用现有规则）
            ├─ 「你命中过 N 天」+ 日期列表（未命中 → 空态文案）
            └─ 平台徽章 id（`<code>`，给反馈 bug 用）
```

**为什么是行内展开而不是弹窗 / 新路由**（三条理由，按重要性排序）：

1. **一致性**：`HistoryList` 已经是「整行按钮 + 行内展开」，玩家已经学会这个交互。
   新开弹窗等于在一个页面上放两种展开语义。
2. **代价**：弹窗需要焦点陷阱、`Esc` 关闭、滚动锁、`aria-modal`、返回键行为——
   项目里没有任何现成实现，这些全是净新增的、可出 bug 的面。
3. **可测**：`BadgeBook.test.ts` 现在用 `querySelector('[data-badge-id]')` 断言渲染结果，
   行内展开让「展开后的内容」用同一个 `root.querySelector` 就能断言，不需要新测试基建。

**展开状态**：`ref<ReadonlySet<string>>`（与 `HistoryList.vue` 第 29 行同款）。
**允许多条同时展开**——`HistoryList` 也是多开的，不引入「手风琴」的新规则。
状态只活在页面内，不进 URL、不持久化（刷新回到全折叠）。

### 1.3 数据来源

| 数据 | 来源 | 说明 |
|---|---|---|
| 徽章本身（名称 / 条件 / 家族 / 稀有度 / `cp`） | `useBadges().badgesByFamily` | 已有，零改动 |
| **命中数 `hits`** | `PRICING[badge.id].hits` | `@huedle/shared` 已导出 |
| 颜色空间大小 | `TOTAL_COLORS`（`@huedle/shared`） | = 16777216 |
| 「哪几天命中过」 | `useHistory().entries` 过滤 `entry.badgeIds.includes(id)` | **不要**用 `restoreScore`——见 F7 |
| 「是否已获得」 | `useBadges().isCollected(id)` | 已有 |

新增一个 composable `useBadgeDetail()`，它是**纯派生**的，不发起任何请求、不读任何存储：

```ts
// apps/web/src/composables/useBadgeDetail.ts （新建）
export interface BadgeHitRecord {
  date: string;   // UTC 'YYYY-MM-DD'
  hex: string;    // 该天抽到的颜色，详情里做小色块
}

export interface BadgeDetail {
  hits: number;                    // PRICING[id].hits；缺定价 → null
  hitDays: BadgeHitRecord[];       // 按日期降序（entries 已是降序）
  firstDay: string | null;         // 最早命中日（= 首次拿到）
  isCollected: boolean;
}

export function useBadgeDetail(): { detailOf: (id: string) => BadgeDetail };
```

`detailOf` 内部按 `id` 做一次 `Map` 缓存（128 条徽章 × N 天历史，每次展开都全扫一遍
是 O(128 × N)，一年 365 天 = 4.7 万次 `includes`，可接受，但缓存后只有 O(N) 一次）。

**「缺定价」的分支必须写**：`PRICING[id]` 理论上一定存在（`compose()` 缺定价会直接抛错，
见 `badges/index.ts`），但 `restoreScore` 会**静默丢弃**存档里已删除的 id
（`scoring.ts` 第 125–127 行）。图鉴里的徽章一定来自 `allBadges`，所以这条分支实际不可达；
仍要写成 `hits: number | null` 并在 UI 上不渲染概率行，**不要** fallback 成 0——
「概率 0」会读成「永远不可能」，比不显示更糟。

### 1.4 UI 结构

```
<li data-badge-id="...">                          ← 现有，加 role="button" 语义
  <button class="w-full ..." :aria-expanded>      ← 新增：整条变可点（现在是 div）
    …现有内容（名称 / 稀有度 / 条件 / CP）…
  </button>

  <div v-if="expanded" class="border-t border-ink-700 p-4 space-y-4">   ← 新增
    <div>真实概率</div>      大字 font-mono + 辅助句
    <div>判定条件</div>      仅 isCollected 时
    <div>你的命中</div>      日期色块 chips ｜ 空态
    <code>badge.id</code>    最底部，text-xs，低对比
  </div>
</li>
```

**注意**：现在 `li` 里已经有 `<span data-testid="badge-cp">` 等元素，
`BadgeBook.test.ts` 第 84 行断言 `[data-collected="false"]` 的数量。
把 `li` 的内容包进 `<button>` 时，**必须保留 `li` 上的 `data-badge-id` / `data-collected`**，
否则测试会红——这是好事（测试在拦我们），但要知道它会红。

### 1.5 逐条中文文案

| 位置 | 文案（中文原文） | 备注 |
|---|---|---|
| 概率区块标题 | `真实概率` | |
| 概率辅助句（大量命中） | `{N} 种颜色里有 {hits} 种` | 例：`1677 万种颜色里有 256 种` |
| 概率辅助句（少量命中，hits ≤ 10000） | `约 {N} 分之 1` | 例：`约 6 万 5 千分之 1`；见 §4 格式化规则 |
| 概率辅助句（hits = TOTAL_COLORS） | `每一种颜色都符合` | 兜底，当前 128 条里没有 |
| 判定条件标题 | `判定条件` | |
| 命中区块标题 | `你的命中` | |
| 命中天数 | `{N} 天` | 紧跟标题右侧 |
| 首次命中 | `首次 {date}` | 仅 `firstDay` 存在时 |
| 命中列表溢出 | `另有 {N} 天` | 只渲染前 12 天，见下 |
| 命中空态 | `还没有命中过` | |
| 未获得的提示 | `抽到之后可以看到判定条件` | 替代原「未获得」胶囊位置 |
| 展开按钮无障碍名 | `展开 {徽章名} 详情` / `收起 {徽章名} 详情` | `:aria-label` |

**「另有 N 天」的取舍**：命中可能横跨一年（`casino-pair` 的 `p = 65.6%`，
按 `PRICING-CURRENT` 是 1101 万色，几乎每天都命中）。日期列表按 12 个截断，
超出的折叠成一句「另有 N 天」。**v1 不做「展开全部」**——详情页里再嵌一层展开会让
`aria-expanded` 嵌套两层，玩家和屏幕阅读器都容易迷路。需要看全部日期的人去的是
「颜色历史」，所以下面第 6 节把「点日期跳到历史行」列为待拍板项。

### 1.6 空状态与边界

| 场景 | 显示 |
|---|---|
| 没有任何历史 | 概率照常显示；「你的命中」显示`还没有命中过`；不显示 `首次`；不显示「另有」 |
| 只有一天记录，且命中 | `1 天` + 那一天（含色块）+ `首次 {date}` |
| 只有一天记录，未命中 | 概率照常显示；「你的命中」显示`还没有命中过` |
| 128 条一条没收集 | 每条都能展开——概率**照常显示**（见下面的决策），条件不显示 |
| 从未命中过某条（已收集了别的） | 同「没有任何历史」那一行的命中区文案；该条本身若未获得，条目仍是降饱和样式 |
| 登录模式读取中 | 沿用页面现有的「正在读取…」，详情不额外加 loading |
| 登录模式读取失败（`error` 非空） | 沿用页面现有错误条与重试；**展开仍然可用**（概率不依赖历史），命中区显示`还没有命中过`是不对的——应显示错误条而不显示命中区。见 §8 待拍板项 Q5 |

**决策：未获得的徽章，详情里显示概率，不显示判定条件。**

理由：概率是**事实**，与「保留发现乐趣」不冲突——玩家知道「这条 1/1677 万」只会更想抽到它，
而不知道条件就仍然保留惊喜。反过来，隐藏概率会让「已获得」和「未获得」的详情页长得不一样，
同一个组件要写两套，且 `BadgeBook.test.ts` 的「未获得不泄露稀有度」断言会变成
「未获得泄露概率」——这条需要一起想清楚（见 §8 Q1）。

## 2. 功能② 成就 / 里程碑

### 2.1 玩家看到什么 / 做什么

在「我的」页看到一排成就卡：已点亮的显示解锁日期，未点亮的显示进度（如 `3 / 7 天`）。
玩家什么都**不用做**——成就随历史自动点亮，它是回看用的，不是任务列表。

### 2.2 核心设计约束：**完全从历史推导，不引入任何存储**

任务给定的约束照做。这里是完整的论证，因为它决定了整个功能的形状。

**① 历史本身就是冻结的，推导天然一致。**
`HistoryItem` 存的是**当时的** `cp` / `rarity` / `badgeIds`（`DESIGN.md` 第 8 节「抽出即定」）。
成就如果只用这 5 个字段，那么「这个人有没有连续 7 天」就是**历史的纯函数**，
不会因为徽章表扩容、定价重跑、`check` 被修而改变。任何需要「重放历史」的成就都会立刻
违反这条——这正是不能做「当时那条颜色按今天的规则值多少分」类成就的原因。

**② 两种模式共用一套逻辑，零分支。**
`useHistory()` 已经把本地 / 登录、缓存、401 回退都收敛掉了（`useHistory.ts` 文件头）。
成就只要消费 `entries`，就**自动**在两种模式下都正确，一行双模式代码都不用写。
如果成就存在服务端，就要新增 API、新增迁移、新增「登录后本地成就怎么合并」这个
和 `DESIGN.md` 第 11.4 节刚论证过不能做的事一模一样的问题。

**③ 没有新的本地键，就没有新的脏数据面。**
`lib/storage.ts` 的整个设计原则是「存储是不可信输入」（文件头第 3–12 行）：
每个读取函数都要做结构守卫、版本检查、逐条容错。多一个 `huedle:achievements`
就多一整套守卫（守卫 `unlockedAt` 的日期格式、守卫数组、守卫版本、处理半写状态），
而它**推导出来的信息与历史完全重复**——两份数据一旦不一致，还要决定谁赢。

**④ 冷启动问题不存在。**
持久化方案必须为「已有 200 天历史的用户」做一次回填：否则他一进来看到
「连续 7 天」未点亮，而历史里明明有 200 天连续。回填要读全部历史并重算，
本质上就是**再写一遍推导逻辑**，只是放在了启动路径上（更慢、更容易出错）。
不持久化则没有这个阶段。

**唯一的代价（明确写出来）**：无法记录「玩家是在哪一刻看到成就点亮的」，
因此**做不了「刚刚解锁」的提示动画**——界面只能显示「解锁于 2026-03-04」。
如果将来一定要做解锁弹提示，正确的做法是**在 `useDailyColor` 写入今日结果的同一条路径上**
把「昨日快照 vs 今日快照的差集」交给一个一次性的 UI 事件（内存态，不落盘），
而不是给成就加持久化。这是我推荐的扩展方向，但**不在 v1 范围内**。

> **结论**：不引入服务端存储，不写新的本地键。若有人坚持要持久化，
> 至少要付出：新 API + 新迁移 + 新守卫 + 冷启动回填 + 双份数据一致性规则，
> 换来的只有「解锁动画」。**不建议。**

### 2.3 数据来源

`useHistory().entries`（唯一数据源）+ `useBadges()` 的两个常量（`allBadges` / `FAMILY_ORDER`）
+ `PRICING[..].rarity`（判断某条徽章是不是神话）。

**不新增任何读取路径**。派生逻辑全在新的纯函数模块里：

```
lib/achievements.ts   （新建，纯函数，零依赖 DOM / localStorage）
  ├─ 成就定义表（id / 家族 / 目标值 / 谓词）
  ├─ deriveAchievements(entries, today) → AchievementState[]
  └─ longestStreak(entries) → number
```

**`today` 必须作为参数注入**（与 `computeHistoryStats` 第 59 行同款）。
理由：`longestStreak` 不需要今天，但**「当前连续」类成就需要**，而且更重要的是——
注入 `today` 之后测试不需要 mock 系统时钟（`streak.test.ts` 整个文件都靠这个约定）。

### 2.4 成就清单（v1，13 条）

分四类。**`target` 是进度分母**，用于画进度条。

| # | id | 名称 | 判定（完整语义见 §5） | target | 进度显示 |
|---|---|---|---|---|---|
| 1 | `days-first` | 第一天 | `totalDays ≥ 1` | 1 | `N / 1` |
| 2 | `days-10` | 十日 | `totalDays ≥ 10` | 10 | `N / 10` |
| 3 | `days-50` | 五十日 | `totalDays ≥ 50` | 50 | `N / 50` |
| 4 | `days-100` | 百日 | `totalDays ≥ 100` | 100 | `N / 100` |
| 5 | `streak-3` | 三连 | `longestStreak ≥ 3` | 3 | `N / 3` |
| 6 | `streak-7` | 七日不辍 | `longestStreak ≥ 7` | 7 | `N / 7` |
| 7 | `streak-30` | 三十日 | `longestStreak ≥ 30` | 30 | `N / 30` |
| 8 | `family-one` | 圆满一家 | 存在 family 使「该家族全部成员 id ⊆ collectedIds」 | 1 | `K / 1` |
| 9 | `family-three` | 三族圆满 | 上述 family 数量 ≥ 3 | 3 | `K / 3` |
| 10 | `badges-10` | 十枚徽章 | `collectedIds ∩ allBadgeIds` 大小 ≥ 10 | 10 | `N / 10` |
| 11 | `badges-50` | 五十枚徽章 | 同上 ≥ 50 | 50 | `N / 50` |
| 12 | `rarity-anomaly-first` | 初见异常 | 存在 `entry.rarity === 'anomaly'` | 1 | `0 / 1` 或 `1 / 1` |
| 13 | `rarity-mythic-first` | 初见神话 | 存在 `entry.rarity === 'mythic'` | 1 | `0 / 1` 或 `1 / 1` |

**为什么是这 13 条**：

- 覆盖任务给的三个例子（连续 7 天 → #6、集齐家族 → #8、首次神话 → #13）；
- **难度阶梯是乘法而不是加法**：天数是「陪伴」，连续是「习惯」，家族是「广度」，
  徽章数是「深度」，稀有度是「运气」。四类维度各自有低门槛入口（#1 / #5 / #8 / #10 / #12），
  不玩到很深也能点亮至少一条；
- **不做「单项 CP 超过 X」**：那需要定义「X」，而 `PRICING-CURRENT` §6.2 正说明
  `max / p99 = 19360×`，任何绝对阈值都会在徽章表变化后失效；
- **不做「某个家族全部集齐」之外的家族成就**（比如「灰阶集齐 5/10」）：
  `family-three` 已经覆盖了「广度」，再加就变成 10 个家族的 10 个进度条，页面会失控。

**数量上限是 13 条**：一个屏幕（手机）能完整看完的量级。成就列表膨胀到 40 条时，
它会从「回看我的轨迹」变成「又一个没做完的清单」。

## 3. 功能③ 颜色时间线

### 3.1 玩家看到什么 / 做什么

在「我的」页看到一条**横向色带**：每天一个小色块，按日期从左到右排，最近的在最右。
左右滑动看更早的日子，悬停 / 键盘聚焦某个色块看到日期与 hex。
**不需要任何操作，它是一眼看完的摘要。**

### 3.2 交互流程

```
我的 /me
  └─ 颜色时间线区块
       ├─ 色带（横向，可滚动，默认滚到最右 = 最新）
       └─ 悬停 / 聚焦某个色块 → title + 就地浮层显示 `2026-03-04 · #002FA7`
```

**为什么是横向而不是纵向**：手机是主要形态，纵向色带要么每格很小（365 格 × 4px = 1460px，
要一直往下滚），要么占满首屏把「颜色历史」推到很下面。横向色带固定在
一个 64–80px 高的条里，滑动手势是手机的原生动作，且**不会挤压页面其他内容**。

**为什么不做成「点击色块跳转到历史行」**：需要 `HistoryList` 暴露受控的展开状态
和滚动锚点，跨组件协调，是净新增的耦合面。v1 不做，列进 §8 Q4。

**滚到最右**：`onMounted` 里 `el.scrollLeft = el.scrollWidth`（最新日期在右侧）。
不引任何滚动库。

### 3.3 数据来源

`useHistory().entries`（已按日期降序）。**不新增请求、不新增存储。**
唯一的加工在纯函数层 `lib/timeline.ts`（新建）：

```ts
// 实现签名：`today` 可选。不传时所有 `isToday` 为 false（函数不读时钟）；
// 组件层用真实 UTC 今天兜底，见 3.4 / 3.7。
buildTimeline(entries, today?) → TimelineDay[]   // 按日期升序，**每一天都占位**

type TimelineDay =
  | { kind: 'entry'; date: string; hex: string; cp: number; rarity: ScoreRarity; isToday: boolean }
  | { kind: 'gap';   date: string; isToday: false }   // 没抽的那天，占位但**没有颜色**
```

`TimelineDay` 是**带判别字段 `kind` 的联合类型**：`entry` 持有 `hex` / `cp` / `rarity`，
`gap` 只有 `date`，且 `isToday` 恒为 `false`——缺口不伪造颜色，也不伪造 `cp` / `rarity`。
组件按 `kind` 渲染成两种节点（见 3.4）。**从最早一天到最晚一天之间的每一天都占一个位置**，
因此 `entries` 里没有的那几天会以 `gap` 的形式出现——这条决定本身见 3.7。

**周 / 月的分组线**：v1 **不做**。`date` 是 UTC 口径，`new Date('YYYY-MM-DD').getDay()`
在 `jsdom` 与浏览器里一致（`YYYY-MM-DD` 被解析为 UTC 午夜），但**「一周从哪天开始」
是一个需要当地决定的策略**（周日 / 周一，且它是游戏日期还是玩家日历日期）。
在 v1 里画分隔线会让每一条线的位置都变成一个可以被反驳的决定，而它带来的信息
（「这里是周末」）玩家自己看日期就知道。列为 §8 Q6。

|---|---|

| 登录模式读取失败 | 整块不渲染（同 §2.7） |
| 读取中 | 不额外显示 loading，沿用页面上已有的「正在读取…」 |

### 3.7 缺口（gap）：为什么**每一天都要占位**

时间线是**日历轴**，不是「有记录的那几天排成一排」。所以从最早一天到最晚一天之间的
**每一天都占一个位置**：有记录的渲染成色块（`kind: 'entry'`），没记录的渲染成
虚线灰块（`kind: 'gap'`）。理由只有一条，但它是决定性的：

> 不画的话，「连续 3 天」与「3 天散在一个月里」在视觉上完全一样——
> 而时间线的全部意义就是显示连续性。

换句话说，去掉缺口之后这条色带仍然好看，但**它不再是时间线**：它退化成
「历史条目的缩略列表」，而那个信息 `HistoryList` 已经有了。缺口的代价是 DOM 数量
从「有记录的天数」变成「跨度天数」（一年 365 个 `<li>`，仍然廉价），换来的是
连续性**可被一眼看见**——这正是功能③存在的理由。

两条边界，明确写清：

- **缺口只补在最早与最晚之间**。最早一天之前、最晚一天之后不补：把色带补到「今天」
  会让长期不抽的玩家看到一大片灰色，而把起点回溯到某个「第一天」则需要先定义它
  （注册日？安装日？）——两个决定都会有人反对，且都不是这条色带要回答的问题。
- **缺口不伪造颜色**。它 `aria-hidden`、没有 `aria-label`、没有背景色，`title` 只说
  `{date} · 没有记录`。「没有」就是「没有」，画成一个低饱和的彩色块会让玩家以为那天抽到了什么。

### 5.3 为什么集成必须由**一个人**做完，而不是「先到先改」

`Profile.vue` 的 `<template v-else>` 块（第 133–221 行）里，②和③要插到**同一个位置**
（统计区之后、颜色历史之前）。如果两个人各自改一遍，必然出现：
一个分支把 section 插在统计区后、另一个插在颜色历史后，合并时顺序由合并顺序决定——
这不是技术问题，但它会让**最终布局变成一个没人决定过的结果**。
所以：**集成者先决定两块的顺序**（推荐的最终顺序见下），一次性插入。

**推荐的 `Profile.vue` 最终顺序**（从上到下）：

```
① 身份区
② 统计区（收集天数 / 当前连续 / 最高 CP / 稀有度分布）      ← 现有
③ 成就           ← ② 功能，插在这里
④ 颜色时间线     ← ③ 功能，插在这里
⑤ 颜色历史       ← 现有 HistoryList
⑥ 清空本地记录   ← 现有
```

理由：「成就」和「统计区」都是**数字型摘要**，放一起；「时间线」是**视觉型摘要**，
紧贴它要概括的「颜色历史」。这样从抽象到具体（数字 → 缩略图 → 明细）是一条直线。

### 5.4 分支隔离的技术保障

- **不要动 `pnpm-lock.yaml` / `packages/shared/**`**：三个功能都不需要新依赖。
- **`ui-copy.test.ts` 会在每次功能分支上跑**：新增的 `.vue` 会被 `import.meta.glob('./**/*.vue')`
  自动扫到（`ui-copy.test.ts` 第 14–18 行），所以**每条分支都会因为别人的新文案而变红**——
  这是预期的。文案自查表见第 6 节。

## 6. 成就判定语义与歧义点

### 6.1 通用语义（先定这四个，13 条都建立在它们之上）

| 量 | 定义 | 实现 |
|---|---|---|
| `days` | `entries` 里**去重后的日期数** | `new Set(entries.map(e => e.date)).size` |
| `collectedIds` | 全部 `entry.badgeIds` 的并集，**不过滤取代** | 与 `useBadges.ts` 第 68–74 行**逐字同口径**，抽成 `lib/achievements.ts` 里可复用的导出，不复制粘贴 |
| `longestStreak` | 全部历史里**最长的连续 UTC 日期段**的长度 | 见 6.2 |
| `unlockedAt(achievement)` | 谓词第一次为真的那个**历史日期**（不是「点亮的时刻」） | 见 6.3 |

### 6.2 `longestStreak` 的定义（**不复用 `computeStreak`**）

**为什么不能复用**：`computeStreak(history, today)` 要求 `today` 在历史里
（`storage.ts` 第 264 行 `if (!days.has(today)) return 0`）。用它算
「曾经连续 7 天」的话，玩家断签第一天，这条成就就会**熄灭**——成就一旦点亮又熄灭，
玩家会认为是 bug。这是唯一正确的选择：技能 / 里程碑类成就必须**闩锁（latch）**。

**定义**：

```
输入：entries（无序或降序皆可）
1. days ← 去重后的 date 集合
2. 把 days 升序排序
3. 扫描：相邻两天若满足 next === previous + 1 天（UTC 日期算术，
   必须用 storage.ts 第 245–248 行 previousUtcDay 同款的
   Date.UTC(y, m-1, d) ± 86400000 算法，不能用本地 Date 加减 —— 会踩夏令时）
   → 当前段 +1；否则当前段重置为 1
4. 返回扫描过的最大值（空集合 → 0）
```

**为什么必须用 UTC 日期算术**：`new Date('2026-03-08')` 是 UTC 午夜，
本地（如 America/New_York）加一天会跨过夏令时切换，出现 `+86400000ms` 后
仍是同一天的本地日期。`storage.ts` 的 `previousUtcDay` 已经踩过这个坑，
新函数**必须复制那个算法**（建议把它从 `storage.ts` export 出来复用，但
storage.ts 的改动会在三个分支的共享写集里——**v1 直接在 `lib/achievements.ts` 里
重写一份 3 行的同名私有函数**，代价是两份实现，收益是零文件冲突。
这个取舍列进 §8 Q3）。

**边界情况（逐条列清）**：

| 输入 | `longestStreak` | 说明 |
|---|---|---|
| `[]` | 0 | |
| `['2026-03-04']` | 1 | |
| `['03-04','03-05','03-06']` | 3 | |
| `['03-01','03-02','03-05','03-06','03-07','03-08']` | 4 | 取最长的段，不是「最近的那段」 |
| `['02-28','03-01']`（平年，2 月 28 天） | 2 | 跨月 |
| `['02-28','02-29','03-01']`（闰年 2028） | 3 | 跨闰日。**必须有这条测试** |
| `['2026-03-04','2026-03-04']`（重复日期） | 1 | 先去重；`loadHistory` 已保证唯一，但函数不能假设 |
| 断签后再连续 | 取**曾经**最长的，不取当前的 | 这就是「闩锁」语义 |

### 6.3 「解锁日期」的定义

每条成就的 `unlockedAt` = **按日期升序遍历历史时，谓词第一次为真的那个日期**。

- **天数类（#1–4）**：升序第 `target` 条记录的日期。
- **连续类（#5–7）**：存在某个**段的结束日** `d`，使该段长度 ≥ target；
  取**最小的那个 `d`**。例：`03-01…03-07` 连续 7 天 → `unlockedAt = '2026-03-07'`；
  之后又断了，再连续 9 天，`unlockedAt` 仍然是 `03-07`。
  **不是**「第一次连续满 7 天中间那天」，是**满 7 天的那一天（段的第 7 天）**。
- **家族 / 徽章数类（#8–11）**：升序扫描，第一次使计数达到 target 的那一天的日期。
- **稀有度类（#12–13）**：第一条 `rarity` 匹配的记录的日期。

**「当前连续」不参与任何成就**。#5–7 全部用 `longestStreak`。
**理由**：`currentStreak` 依赖 `utcDate()`，同一个历史在今天和明天会得到不同的结论——
成就是「你曾经做到过」，不该被今天的懒惰没收。

### 6.4 歧义点（明确标出，不假装没有）

| # | 歧义 | 本文的裁决 | 是否真的无歧义 |
|---|---|---|---|
| A1 | 「曾经连续 7 天」断签后还算不算 | **算**（闩锁语义，§6.2） | ✅ 裁决明确，但**这是我替你做的决定**，业务上可以反对 |

## 7. 概率展示规则

### 7.1 展示什么

**只展示概率，不展示 `ep` / `cp`。**

对每条徽章，用 `hits` 与 `TOTAL_COLORS` 得到：

```
占比 q = hits / TOTAL_COLORS
```

三条规则，按优先级：

| 条件 | 主展示（大字） | 辅助句 |
|---|---|---|
| `q ≥ 0.5` | `{pct}%` | `{N} 种颜色里有 {hits} 种` |
| `0.01 ≤ q < 0.5` | `{pct}%` | `{N} 种颜色里有 {hits} 种` |
| `q < 0.01` 且 `hits ≤ 9999` | `1 / {total / hits}` | `约 {人话的 N} 分之 1` |
| `hits ≥ 10000` | `{pct}%` | `约 {人话的 N} 分之 1` |

其中 `pct` 用 2 位有效数字（`(q*100).toPrecision(2)`）。

**实例**（取自真实 `PRICING`）：

| 徽章 | `hits` | `q` | 主展示 | 辅助句 |
|---|---|---|---|---|
| `casino-six-kind` | 16 | 9.5e-7 | `1 / 1,048,576` | `约 105 万分之 1` |
| `culture-klein-blue` | 1 | 6.0e-8 | `1 / 16,777,216` | `约 1677 万分之 1` |
| `pure-only-red` | 255 | 1.5e-5 | `1 / 65,793` | `约 6.6 万分之 1` |
| `pattern-half-loop` | 4096 | 2.4e-4 | `1 / 4,096` | `约 4100 分之 1` |
| `casino-royal` | 720 | 4.3e-5 | `1 / 23,302` | `约 2.3 万分之 1` |

> ⚠️ **本节原先把千分之一数写成了 `1 / {hits}`，那是错的**——`hits` 是「命中多少种颜色」，
> 不是「多少分之一」。正确的千分之一数是 `total / hits`。
>
> 这个错误之所以一直没被发现，是因为样例里 `pattern-half-loop`（hits = 4096）
> **碰巧**是对的：16777216 ÷ 4096 = 4096。其余四条全错，其中 `hits = 1` 那条
> 会把**最稀有的徽章**显示成 `1 / 1`——读起来是「必然抽中」，与真相正好相反。
>
> 教训：**给公式配样例时，样例要能区分"公式对"和"公式碰巧对"**。
| `channel-all-high` | 2097152 | 0.125 | `12%` | `1677 万种颜色里有 209 万种` |
| `casino-pair` | 11011456 | 0.656 | `66%` | `1677 万种颜色里有 1101 万种` |
| `math-coprime-trinity` | ~13940000 | 0.831 | `83%` | `1677 万种颜色里有 1394 万种` |

> ⚠️ 上表的 `q` 与 `hits` 中，`hits ≤ 10000` 的都是从 `pricing.gen.ts` 抄的真实值；
> 两处 `~` 是 `PRICING-CURRENT` 的百分比反推，**实现时一律从 `PRICING` 读，不要抄本文**。

### 7.2 数字怎么写成「人话」

**为什么不能直接写 `1 / 16777216`**：`16777216` 有 8 位数字，玩家读到的是「差不多一千多万」，
但拿不到「这是一千六百七十七万」这个精确感。而 `1677 万` 一眼可读，且**恰好**是这个数的
中文直觉。同理 `1 / 65536` → `约 6.6 万分之 1`。

中文大数换算（`lib/probability.ts` 私有）：

```
≥ 1 亿     → `{x.y} 亿`（1 位小数）
≥ 1 万     → `{x.y} 万`（1 位小数）
≥ 1 千     → `{x.y} 千`
其余        → 原数字（千位分隔）
```

**不引 `Intl.NumberFormat('zh-CN', { notation: 'compact' })`**：
不同浏览器 / Node 版本对中文紧凑格式的舍入与单位选择不一致
（`16777216` 可能渲染成 `1678万` 或 `1677.7万`），而这是**会被测试断言**的字符串。
手写 4 行的换算表是确定的。

### 7.3 与 `formatCp` 的关系（**明确不动它**）

| | `formatCp`（现有） | 概率展示（本次新增） |
|---|---|---|
| 位置 | `lib/format.ts` 第 11–14 行 | `lib/probability.ts`（新文件） |
| 输入 | `cp` / `ep`（可达 1.79×10⁹） | `hits`（1 – 16777216） |
| 输出 | 千位分隔整数 `1,790,000,000` | 分数 / 百分比 + 人话大数 |
| 调用点 | `BadgeBook.vue` / `BadgeList.vue` / `HistoryList.vue` / `Profile.vue` | **仅** `BadgeDetailPanel.vue` |
| 本次是否改 | **不改**，一行都不改 | —— |

**为什么不能顺手改全局 CP 显示**：`formatCp` 的输出被四个既有页面共用，
且 `PRICING-SPEC.md` §9 明确把「CP 怎么展示」列为**未决项**：

> `ep` 是十进制大数（最稀有的徽章可达 `1.7×10⁹`）。展示层需要处理：千位分隔符，
> 或对数压缩，或只显示数量级。**尚未决定，本规范不约束展示。**

`PRICING-CURRENT.md` §6.2 进一步实证了这个问题（`max / p99 = 19360×`，
`mythic` 档内部跨 4.5 个数量级）。**这是一个需要单独拍板、单独一次提交去做的决策**，
把它塞进「徽章详情」这个功能里，会让一个已经够复杂的设计变更混进三个功能的并行开发。
本次只做一件事：**详情页展示概率，CP 维持现状。**

> **注意**：详情页不会出现 CP，但图鉴条目上**仍然有** CP（现状）。
> 于是同一个徽章在一条目里出现两个数字（CP 和概率）。这是可接受的——
> 它们量纲不同（CP 是「稀有度分数」，概率是「真实占比」），且 §8 Q9 把
> 「详情页要不要也显示 CP」列为待拍板。

### 7.4 格式化函数的签名

```ts
// apps/web/src/lib/probability.ts （新建）
/** 概率的主展示：`1 / 255`、`12%`、`0.045%`。 */
export function formatProbability(hits: number, total?: number): string;
/** 概率的辅助句：`约 6.6 万分之 1`、`1677 万种颜色里有 256 种`。 */
export function formatProbabilityHint(hits: number, total?: number): string;
/** 大数的人话写法：16777216 → `1677 万`。 */
export function formatCount(n: number): string;
```

`total` 默认 `TOTAL_COLORS`，可注入以便测试用小数色域。
**`hits === 0` 必须单测**（虽然不可达）：返回 `0%`，而不是 `1 / 0` 或 `Infinity`。

这些是集成后仍然存在、**本次刻意不修**的问题。记在这里是为了让下一个人能在动手前
知道触发条件与代价，而不是重新发现一遍。

### 9.1 登录模式冷启动访问 `/badges` 会多发一次 `GET /api/history`

**触发条件**：登录模式 + 历史缓存未命中（当天第一次打开、或跨天后第一次）+
直接访问 `/badges`（徽章详情页）。

**原因**：`useBadgeDetail()` 同时调用了 `useBadges()` 与 `useHistory()`。
`useHistory()` 是**每次调用各持一份内部状态**的（`entries` / `isLoading` / `error`
都是 `useHistory()` 函数体内的 `ref`，不是模块级共享），所以这两次调用各有一个
历史实例、各发一次请求。只有当第一个实例的请求先落地、把当日缓存写进
`localStorage` 之后，第二个实例才可能命中缓存——同一轮渲染里它们几乎同时发起，
因此缓存命中不了。

**代价**：一次多余的 `GET /api/history`。数据库在美东，实测约 740ms，所以
冷启动的 `/badges` 会比必要情况晚一点拿全数据；玩家侧的可见影响很小（两个实例
最终拿到同一份历史），主要代价是**请求数翻倍**与一次无谓的等待。

**为什么本次不修**：收口需要把 `useHistory` 的内部状态（至少是
`entries` / `isLoading` / `error` 与 in-flight promise）提升为**模块级共享**，
让它变成「按账户 + 日期缓存」的进程内单例。这个改动会同时影响
`Profile` / `BadgeBook` / `useBadgeDetail` 三个消费方的生命周期语义
（组件卸载后状态要不要留、换账户怎么失效、401 回退怎么清），
风险面明显大于本次「把两个已经验收过的组件接进页面」。
**这是一次独立重构，不是集成的顺手修补。**
