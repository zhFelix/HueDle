# HueDle 定价规范（Probability Pricing）

> 本文档冻结「CP 从哪来、稀有度怎么定」的规则。
> 依据：[RNGdle 研究笔记](./research/RNGDLE-NOTES.md) 第 3–4 节。
>
> **背景**：v2 的 CP 是作者在 rarity 区间内手填、并封顶在 800，导致一条
> `p = 6×10⁻⁸` 的规则和一条 `p = 0.27` 的规则只差一个数量级。实测后果：
> `#000000` 与 `#002FA7` **抽到概率完全相同（都是 1/2²⁴）**，CP 却是 2337 vs 876，
> 稀有度差两档。本规范取代手填 CP。

---

## 1. 为什么改成概率定价

两个候选模型：

| 模型 | 「稀有度」衡量什么 |
|---|---|
| 手填 CP 求和（v2） | **命中规则的条数与作者主观赋值** |
| 概率定价（本规范） | **抽到它的真实难度** |

选后者。理由：

1. **同概率必然同分** —— 这是稀有度这个词的最低要求，v2 做不到；
2. **徽章的权重正比于规则自身的稀有度** —— 常见规则的贡献自动趋近于噪声；
3. **作者不再需要猜分值** —— 只写规则，权重由实测概率导出；
4. 与参考实现（RNGdle 的 `EP = 100 / p`）一致，可直接对照验证。

---

## 2. 核心公式

颜色空间大小：

```
N = 2^24 = 16,777,216
```

每条徽章的**精确命中数** `hits` 由全色域枚举得出（`0 ≤ hits ≤ N`）。

```
p  = hits / N            # 命中概率
ep = 100 / p             # 期望点数，等价于 100 * N / hits
```

`ep` 就是该徽章的 CP。**它是推导值，不是手填值。**

> `ep = 100/p` 这条「价格律」的直觉：EP × p ≡ 100，
> 即每条徽章在完全随机的抽取下**每抽的期望贡献相同**，不存在「刷分」策略。
> 分数差异只来自「你抽到了多稀有的组合」。

---

## 3. 徽章稀有度：EP 的十进制分档

沿用 RNGdle 的阈值（注意这些阈值本质是关于 `p` 的，与空间大小无关）：

| `ep` 区间 | 等价 `p` | `BadgeRarity` |
|---|---|---|
| `< 10³` | `p > 0.1` | `common` |
| `< 10⁴` | `p > 0.01` | `uncommon` |
| `< 10⁵` | `p > 0.001` | `rare` |
| `< 10⁶` | `p > 10⁻⁴` | `epic` |
| `< 10⁷` | `p > 10⁻⁵` | `anomaly` |
| `≥ 10⁷` | `p ≤ 10⁻⁵` | `mythic` |

**徽章的 `rarity` 不再手填，由 `ep` 导出。**

---

## 4. 抽取稀有度：总分的百分位

总分 `cp = Σ ep(计分保留的徽章)`（先按 `group` 取代，再求和）。

抽取的稀有度**不看绝对值，看百分位**：

| 百分位 | `ScoreRarity` |
|---|---|
| `< 1` | `trash` |
| `< 50` | `common` |
| `< 75` | `uncommon` |
| `< 90` | `rare` |
| `< 95` | `epic` |
| `< 99` | `anomaly` |
| `≥ 99` | `mythic` |

百分位由枚举时统计的**总分分布**给出。

### 4.1 为什么用百分位而不是绝对阈值

- 绝对阈值需要「反推 + 冻结 + 每次扩表重算」，且徽章表一变就失效；
- 百分位是**声明式**的：「神话 = 前 1%」，永远成立；
- RNGdle 就是这么做的（`{trash:1, common:50, uncommon:75, rare:90, epic:95, anomaly:99}`）。

### 4.2 类型拆分（本次一并修正）

`BadgeRarity` 与 `ScoreRarity` 是**两套不同的东西**、阈值互不相干，
必须拆成两个类型（v1 里它们共用一个 `Rarity`，是我早期标记过的设计异味）：

```ts
export type BadgeRarity = 'common' | 'uncommon' | 'rare' | 'epic' | 'anomaly' | 'mythic';
export type ScoreRarity = 'trash' | BadgeRarity;
```

## 5. 数据存储方式

**徽章定义与定价数据分离**（与 RNGdle 的 `BADGE_DEFINITIONS` / `SCORED_BADGES` 一致）：

| 文件 | 性质 | 内容 |
|---|---|---|
| `src/badges/<family>.ts` | **人工维护** | `id/name/description/family/group/check`，**不含 `cp`/`rarity`** |
| `src/pricing.gen.ts` | **自动生成** | `{ [id]: { hits, ep, rarity } }` |

`allBadges` 由两者合成。作者只写规则，权重全部来自实测。

> 好处：改一条 `check` 之后，只要重跑枚举就能发现它的 `ep` 变了——
> 而手填模型下，改了规则但忘了改 CP 是完全静默的。

## 6. 交付物与命令

| 命令 | 作用 |
|---|---|
| `pnpm -C packages/shared run enumerate` | 全色域枚举，重新生成 `pricing.gen.ts` 与分位表 |
| `pnpm -C packages/shared run docs` | 用最新定价重新生成 `docs/BADGES.md` |
| `pnpm -C packages/shared test` | 全量测试 |

枚举还必须产出**变更报告**（`docs/research/PRICING-MIGRATION.md`）：
逐条列出「旧 rarity/CP → 新 rarity/EP」，并给出分数分布摘要，
便于人工复核模型是否合理，**再**决定是否落地。

## 7. 验收要点

1. **同概率同分**：任意两条 `hits` 相同的徽章，`ep` 必须相同。
2. **单调性**：`hits` 越少 → `ep` 越大。（`ep = 100 * N / hits` 天然满足）
3. **无空徽章**：任何 `hits === 0` 的徽章必须报错，因为它永远不会命中。
   （例外：`hits === N` 是合法的，`ep = 100`。）
4. **取代组仍生效**：同 group 取 `ep` 最大者。
5. **百分位自洽**：用分位表反算，各档占比必须落在其定义区间内。
6. **可复现**：同一份徽章代码连续枚举两次，结果逐字节相同。

---

## 8. 已知影响（需人工复核）

按新模型，**手填的 rarity 配额限制（mythic ≤ 4、每家族 epic ≤ 2）全部失效**——
稀有度不再由作者选择，而由规则的概率决定。这带来两个后果：

- ✅ 不再需要配额约束（膨胀由定价本身消除）；
- ⚠️ 部分徽章的档位会**大幅变动**。例如 `pattern-half-loop`（前三位 = 后三位，
  仅 `16³ = 4096` 色命中，`p ≈ 2.4×10⁻⁴`）在手填模型下是 `mythic`，
  按新模型 `ep ≈ 4.1×10⁵` 落在 `epic`。

**这正是需要先出变更报告、再落地的原因。**

---

## 9. 遗留问题

- `ep` 是十进制大数（最稀有的徽章可达 `1.7×10⁹`）。展示层需要处理：
  千位分隔符，或对数压缩，或只显示数量级。**尚未决定，本规范不约束展示。**
- 总分 = EP 之和，而 EP 跨度达 7 个数量级 → 总分会被最稀有的那一条徽章主导。
  这是 RNGdle 的既有行为，属于**预期**，不是缺陷；但需要复核总分分布是否有意义
  （若绝大多数颜色挤在同一档，百分位分档就退化了）。
