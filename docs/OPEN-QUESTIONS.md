# 待裁决的两个问题（供外部讨论）

写这份文档是为了把两个**悬而未决的技术决策**连同完整背景交出去，让不了解这个项目的人（或另一个 AI）能独立判断。

两个问题都**不影响功能的正确性**——它们分别是「浪费时间的风险」和「维护性的成本」。

---

## 项目背景（读这两个问题所需的最小上下文）

**HueDle** 是一个每日随机颜色收集游戏。每天全局随机出一个颜色，玩家揭晓后获得这个颜色，以及**它命中的全部徽章**。

**徽章**是这套系统的核心：

- 共 **128 条**，每条是一个判定函数 `check(color) => boolean`，用 TypeScript 写在
  `packages/shared/src/badges/<family>.ts`（10 个家族文件）
- **颜色空间是有限的**：RGB 各 8 位 = **2²⁴ = 16,777,216 色**
- 因此每条徽章的命中数 `hits` 可以**穷举算出精确值**（不是采样估计）
- 稀有度与得分 `cp` 由 `hits` 推导：`p = hits / 2²⁴`，`ep = 100 / p`
- 这些值存在生成文件 `packages/shared/src/pricing.gen.ts` 里

**加一条新徽章**要改 TypeScript 源码，然后重跑全色域枚举（约 **5.4 分钟**）重新生成定价。
有一个本地工具 `tools/admin` 把这条流水线自动化了。

---

# 问题一：`evalHelpers` 漂移

## 系统里有什么

加徽章有**两条路径**：

| | 输入 | 说明 |
|---|---|---|
| **结构化** | `when`：JSON 表达式树 | 默认路径。工具把它编译成**两个**产物：<br>① `toSource()` → 写进家族文件的 `check` 源码<br>② `toPredicate()` → 内存里的函数，**干跑**用 |
| **手写** | `handwritten.check`：一段 TS 表达式 | 约 **27%** 的徽章形态（如 casino 顺子）JSON 表达不了，只能手写。**可以引用目标家族文件里的私有 helper** |

**「干跑」是什么**：写盘**之前**，把候选条件在全部 16,777,216 个颜色上跑一遍，得到精确的
`hits`、并检查是否恒真/恒假/与既有徽章构成蕴含。**这一步在写盘之前**，所以坏条件不会污染仓库。

## 问题

手写路径下，干跑需要求值 `handwritten.check`。但**此刻那段代码还没被写进家族文件**，
所以它引用的私有 helper（比如 `casino.ts` 里的 `onRanks`）**不在作用域里**。

解决办法是让作者**额外提供一份 JS 副本**：

```jsonc
{
  "handwritten": {
    "check": "onRanks(c, counts => counts.filter(n => n >= 5).length === 1)",
    "evalHelpers": {
      // ↓ 这份副本【只用于干跑求值】，不会写进仓库
      "onRanks": "color => { const counts = rankCounts(color); return ... }"
    }
  }
}
```

**工具能校验的**：这个 helper 名字**确实存在于目标家族文件里**（否则写盘前就拒绝）。

**工具不能校验的**：**你给的副本和文件里的真品语义相同。**

## 后果

```
干跑用的    evalHelpers 里作者写的副本     ← 可能和真品不一样
写盘后跑的  家族文件里真正的 helper        ← 这才是生效的
```

如果两者不一致：

1. 干跑算出的 `hits` 是**错的**（不是真值）
2. 干跑可能**通过**——于是流水线继续：写盘 → `tsc` → **枚举**
3. 枚举用**真品**算，得到**真的** `hits`
4. 如果真值不满足断言（例如 `hits === 0`，或与既有徽章构成蕴含），**枚举阶段失败**
5. 流水线**自动回滚**，仓库回到开跑前

**所以不会污染仓库**——损失是**大约 11 分钟**（干跑 + tsc + 2× 枚举 ≈ 5.4 分钟/次）白跑。

## 已知的真实案例

实现这个工具的 agent 自己承认：**它在演示脚本里提供的 `rankCounts` 副本就是简化的，与真品不同。**
（它成功的那次用的 `exactHex` 副本是对的。）

也就是说**这不是理论风险，已经发生过一次**——只是那次没有触发失败。

## 两个选项

### A. 修：从文件里抽取真正的实现来求值

那个 helper **本来就必须已存在于目标家族文件**（工具已在校验这一点）。所以可以让工具
**读取那个函数的源码文本**，直接求值，而不是信任作者给的副本。

- **收益**：漂移**从根上消失**。干跑的结果与枚举必然一致。
- **代价**：需要从 TypeScript 源码里抽取一个函数体（括号匹配）。**有解析失败的风险**——
  比如 helper 里含嵌套模板字符串、正则字面量里的花括号等。
  而且解析失败时必须有明确的降级（报错，而不是悄悄用副本）。

### B. 不修：文档记录，接受

- **收益**：零实现风险。
- **代价**：每次手写一个引用私有 helper 的徽章，都有一次白跑 11 分钟的风险。

### 可能的中间选项（未评估）

保留 `evalHelpers`，但工具**额外读一遍文件里的实现**，如果发现两者不可能等价就**警告**。
问题：工具无法判断"语义等价"（这需要定理证明或穷举两者在 2²⁴ 上的行为——那本身就是一次干跑）。

## 需要判断的标准

**手写路径、且引用家族私有 helper 的徽章，出现的频率有多高？**

- 很少 → 不值得修
- 经常 → 值得

参考数据：现有 128 条里，**34 条**用了家族文件的私有 helper
（`onRanks` 11、`exactHex` 10、`spread` 5、`allCharsIn` 3、`hasTripleRun` 2、其余各 1）。

# 问题二：后台侧栏的「双名」

## 系统里有什么

`tools/admin` 有一个**只读统计 UI**——一个本地控制台式页面：

```
┌─────────────────────────────────────────────────┐
│ 顶栏：标题 + 连接信息 + 窗口切换 + 刷新            │
├────────────┬────────────────────────────────────┤
│ 概览        │  选中项的详情                       │
│ M1 抽取量…  │  标题 + 「问：…」+ 表格 + 注         │
│ M2 新增…    │                                     │
│ …          │                                     │
└────────────┴────────────────────────────────────┘
```

它由本地服务**服务端渲染**，**零前端 JS**（交互全靠 `<a href>` 与 `<details>`）。
这是刻意的：同一套渲染还用在一个 `file://` 直接打开的静态报告上，那个场景下 JS 没有意义。

**指标共 9 项**：概览 + M1–M8。每项在 `stats.ts` 里自带一句「回答什么问题」。

## 问题

侧栏和卡片用了**两套名字**：

```
侧栏（导航）    M1  抽取量与唯一约束
卡片（正文）    M1  每日抽取量 + 唯一约束哨兵
```

侧栏那一套是**新建的常量** `UI_NAV_LABELS`，与 `stats.ts` 里的标题是两份独立数据。

## 为什么会这样

有一条测试：

```ts
// 断言「右栏只渲染选中的那一项」
expect(html).not.toContain(escapeHtml(otherMetric.title));
```

**这条断言是这次布局改动的核心验收**——它是"一次只看一个"这句话的可检查形式。

但如果侧栏也用完整标题，**9 个指标的标题会全部出现在页面上**，这条断言就永远失败。

所以实现者新建了短名，绕开冲突。

## 两难

**反对（这是问题）**：同一件事有两个名字，未来必然漂移。
改了指标标题、忘了改侧栏，界面上就出现两套说法。而且**是断言的设计扭曲了实现**——
这通常是反的：断言应该描述意图，不该决定实现。

**支持（这不是问题）**：控制台的导航标签**本来就应该比正文标题短**。侧栏宽度有限，
标签是"分类名"不是"标题"。而且这些指标名极少变动。

## 两个选项

### A. 侧栏用完整标题，改断言的写法

把验收断言从「其它指标的**标题**不在页面上」改成
「页面上**恰好有一个** `.card` 元素」（实现者其实**已经在做**这个检查，只是没当主断言）。

- **收益**：名字只有一份，不会漂移。
- **代价**：侧栏变长（最长的一条 `M1 每日抽取量 + 唯一约束哨兵` 在 9 项的侧栏里要换行或截断）。
  窄屏下侧栏会变成横向标签条，长度问题更明显。

### B. 保留短名，把它当作有意的设计

- **收益**：侧栏紧凑；符合控制台惯例。
- **代价**：两份数据要同步维护。可能需要**一条测试**来强制同步
  （例如断言 `UI_NAV_LABELS` 的键集合与 `stats.ts` 的指标 id 集合相等——
  这能挡住"加了新指标忘了加短名"，但挡不住"改了标题忘了改短名"）。

## 需要判断的标准

**侧栏用短名，是有意的设计，还是为了迁就断言？**

- 是**有意的设计** → 选 B（并考虑加一条键集合同步的测试）
- 是**迁就断言** → 选 A（并接受侧栏变长）
