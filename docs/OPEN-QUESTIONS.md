# 待裁决的问题（供外部讨论）

写这份文档是为了把**悬而未决的技术决策**连同完整背景交出去，让不了解这个项目的人（或另一个 AI）能独立判断。

## 这份文档怎么用

**约定：项目里所有有争议的决策都写在这里**，不留在线下讨论里。

每个问题按固定四段写：

```
【争议】        一句话说清争的是什么
【我的判断】    倾向怎么做 + 理由
【另一种合理做法】  反面是什么、代价在哪
【判据】        该用什么标准决定
```

**第四段最重要。**前两段只是我的立场——如果读的人只看到我的理由，这个讨论就没有意义。
**判断的标准必须是可观测的东西**（使用频率、维护成本、出错概率），不是"我觉得"。

**每条都要自带完整背景**，不假设读者读过这个仓库、或读过之前任何一轮对话。

**已决议的不留在这里。**决议后移到 `docs/resolved/`（该目录被 git 忽略）。
**本文档只放还没定的。**

## 一：改了徽章的 `check` 却忘了重跑枚举，默认测试能发现吗？

### 背景（读这一条所需的最小上下文）

**HueDle** 是每日随机颜色收集游戏。徽章是判定函数 `check(color) => boolean`，写在
`packages/shared/src/badges/<family>.ts`（10 个家族文件，共 128 条）。

每条徽章的命中数 `hits` **不是手写的**——它由**枚举**（遍历全部 2²⁴ 个颜色）算出，
连同 `ep`、`rarity` 一起写进生成文件 `packages/shared/src/pricing.gen.ts`。

```
家族文件里的 check   ──枚举（~8 分钟）──→  pricing.gen.ts 里的 hits / ep / rarity
```

**所以 `pricing.gen.ts` 是 `check` 的派生数据。**改了 `check` 而不重跑枚举，
它就是**过期的派生数据**。

（「预先算好」这件事本身是有意的：玩家抽到颜色的那一刻要立刻知道他命中哪些徽章、
得多少分。运行时不可能现场枚举 2²⁴ 个颜色。）

### 争议

**要不要让默认的测试套件能发现「`pricing.gen.ts` 与当前 `check` 不一致」？**

### 已确认的事实

**改 `check` 后不重跑枚举，默认测试不会红。**核实过程：

| 检查点 | 它比的是什么 | 能发现吗 |
|---|---|---|
| `registry.test.ts:57`（cp/rarity 一致） | `badge.cp` vs `PRICING[id].ep` | ❌ **两者都来自 pricing，永远自洽** |
| `registry.test.ts:68`（ep 公式一致） | `ep` vs `epFromHits(hits)` | ❌ 同样只读 pricing |
| `registry.test.ts:78/84/93` | 有无死徽章 / 单调性 / 同 hits 同 ep | ❌ 同样只读 pricing |
| `registry.test.ts:168` | group 内是否有颜色同时命中 ≥2 名成员 | ❌ **早停找 witness，不计数** |
| `casino.test.ts:264` | 类似，早停 | ❌ 不计数 |

**默认套件里没有任何东西重算 `hits`。**

真正做交叉校验的是 `packages/shared/scripts/supersession.test.ts:135`——
它**完整枚举**一遍，然后比 `实测 hits` vs `PRICING[id].hits`。但：

- 它在 `scripts/`，而默认测试范围是 `include: ['src/**/*.test.ts']` → **不在默认套件里**
- 它只在**加徽章流水线的第 9 步**（`supersession`）跑

**所以：不走流水线、手改 `check`、跑一次 `pnpm -C packages/shared test` → 全绿，
而定价表已经过期。**

### 【我的判断】加，但不要用枚举来加

前三个选项都有明显缺陷，我倾向第四个：

| | 方案 | 问题 |
|---|---|---|
| A | 默认套件里做**抽样**交叉校验（如 150k 采样） | **只能发现大偏差**。改一个边界条件让 `hits` 从 4096 变 4000，采样看不出来——**给了一种虚假的安全感** |
| B | 把 supersession 的完整校验纳入默认套件 | **8 分钟**。默认 `test` 是几十秒的东西，塞一个 8 分钟的进去会让人不再跑它 |
| C | 不改，靠"改 check 必须走流水线"这条纪律 | 纪律不是机制。这个项目里所有事故都是**纪律没兜住**的那类 |
| **D** | **指纹**：枚举时把「全部 `check` 源码 + family 归属的哈希」写进 `pricing.gen.ts`；默认 test 里比指纹 | 秒级，**且不需要重新枚举** |

**D 的做法**：`pricing.gen.ts` 里多一个字段，例如

```ts
export const SOURCE_FINGERPRINT = '<sha256 of 全部 check 源码 + family 归属>';
```

默认 test 里重新算一遍当前源码的指纹，与它比较。**不等 = `check` 改过而没重跑枚举。**

**它精确抓住「改了没重跑」，而不判断「定价对不对」**——后者才需要 8 分钟。这正是要的粒度。

### 【另一种合理做法】不加

- **流水线本来就是唯一正确的加/改徽章入口**：它第 6 步是枚举，第 9 步是交叉校验。
  **绕开工具手改源码本来就是非常规操作。**
- 指纹会**变成一个新的—致性负担**：指纹本身也可能与源码不同步
  ——那正是孤儿条目那类问题的形状：**修一个不一致的时候，引入一个新的可能不一致**
- `pricing.gen.ts` 是**生成文件**。往里加"源指纹"意味着生成器要知道它的输入是什么，
  这个耦合不是免费的

### 【判据】

**手改 `check` 这件事，在实际工作流里会不会发生？**

- **不会**（一律走流水线）→ 选「不加」。没有绕开机制的时候，就不需要一个检测绕开的机制
- **会**（改一个边界值、试参数、调一个判定）→ 选 **D**。
  因为那种改动**看起来"很小、不像是要跑 8 分钟枚举的事"**，
  而它恰恰是「改完就忘了重跑」的高发场景

**相关的旁证（事实）**：这个项目里已经发生过三次同类问题，都是「派生数据与源不一致而测试全绿」：

| 事故 | 发现方式 |
|---|---|
| README 写 126 条徽章（实际 128） | 人工 |
| `pricing.gen.ts` 留下孤儿条目 `extreme-404` | 人工，**只差一步被提交** |
| 生成的家族文档表格与代码不一致 | 人工 |

**就这 3 次而言**，没有一次是被测试发现的。

## 下次往这里写什么

> ⚠️ **以下是判断，不是规则。**署名 agent、日期 2026-10-05。
> 依据只有当时那三个案例。**如果你按它筛掉了一个后来证明该写进来的问题，那就是它错了。**


**不是所有技术选择都该进这份文档。**判据是：

| 该进 | 不该进 |
|---|---|
| 有两种合理做法、各有代价，需要人拍板 | 只有一种做法，或另一种明显更差 |
| 结论依赖**项目之外的判断**（产品取向、使用频率预期） | 纯技术事实问题，查一下就有答案 |
| 错了的代价**不能立刻看出来**（它可能很久以后才显现） | 错了当场就红，改回来很便宜 |

**当时认为**第 3 条尤其值得留意，理由是——就当时见过的事故而言，**真正伤人的不是"写错了"，
而是"写错了但所有测试都是绿的"**：

```
README 写 126 条徽章（实际 128）              人工发现
pricing.gen.ts 留下孤儿条目 extreme-404       人工发现，只差一步被提交
最稀有徽章被显示成「1 / 1 = 必然抽中」          人工审设计文档时发现
```

**就那 4 次而言**，没有一次是被测试发现的。

（限定词是必要的：这是 4 个案例的统计，**不是一条规律**。）

**当时的推论**：所以进这份文档的，应该主要是**测试看不见的那类决定**。
