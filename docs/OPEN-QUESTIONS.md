# 待裁决的问题（供外部讨论）

写这份文档是为了把**悬而未决的技术决策**连同完整背景交出去，让不了解这个项目的人（或另一个 AI）能独立判断。

## 这份文档怎么用

**约定：项目里所有有争议的决策都写在这里**，不留在线下讨论里。

每个问题按固定四段写：

```
【争议】        一句话说清争的是什么
【我的判断】    倾向怎么做 + 理由
【另一种合理做法】  反面是什么、代价在哪
【判据】        该用什么标准决定
```

**第四段最重要。**前两段只是我的立场——如果读的人只看到我的理由，这个讨论就没有意义。
**判断的标准必须是可观测的东西**（使用频率、维护成本、出错概率），不是"我觉得"。

**每条都要自带完整背景**，不假设读者读过这个仓库、或读过之前任何一轮对话。

## 一：`/api/health` 要不要真的探一次数据库？

### 背景

`apps/api` 部署在 Railway，数据库在 Supabase（悉尼）。
健康检查端点是 `GET /api/health`，它现在**只回 `{ ok: true }`，不碰数据库**。

### 争议

**要不要让它查一次数据库（`SELECT 1`），不通就返回 503？**

### 已确认的事实

**2026-10-05 一天之内，这个缺口骗过了两次：**

| 事件 | 现象 |
|---|---|
| 换了数据库密码，Railway 的环境变量没跟上 | `/api/health` → **200**（一切正常的样子），而**注册 → 500**。是我去试注册才发现的 |
| 本机 IPv6 掉线，直连域名解析失败 | 同上。`/api/health` 仍然 200 |

**根因**：健康检查不碰任何依赖，所以它无法区分「服务活着」和「服务能用」。

### 【我的判断】加

一次 `SELECT 1`，失败返回 503。改动极小，而且它把两个真实的故障从"要去点登录才发现"
变成"一眼就能看到"。

### 【另一种合理做法】不加

- **健康检查的语义本来就是"进程活着"**，不是"依赖都通"。Kubernetes 那类编排里，
  依赖不通**不应该**让 liveness probe 失败——那会导致容器被反复重启，
  而重启并不会让数据库回来。**这是有正当理由的通行做法。**
- Railway 有自己的部署健康检查与日志，出问题时看日志也能定位
- 每次探活多一次跨洋往返（悉尼，约 350ms）——虽然探活频率低，不是问题

### 【判据】

**这个项目有没有"独立的存活探针"需求（编排器靠它决定重启）？**

- **有** → 选「不加」，或者**另开一个 `/api/ready`** 放依赖检查（`/api/health` 保持轻量）
- **没有**（Railway 的重启由部署流程决定，不依赖这个端点）→ 选「加」，
  因为它唯一的作用就是给人看，而人需要知道的是"能不能用"

**另一个角度**：这个端点现在是**给人看的还是给机器看的**？
现在的实现（永远 200）对机器没用（无法判断依赖），对人也没用（会有假绿灯）。

## 二：Railway 的 Watch Paths 要不要写进部署文档？

> ⚪ **本条暂时悬空。**Railway 已于 2026-10-06 停用。
> 它只在**哪天重新部署到 Railway** 时才重新成立。
> **保留而不删除**，是因为它的失败模式（改构建配置的提交被静默跳过）
> 在任何「从 Git 自动构建」的平台上都成立，不只是 Railway。

### 背景

Railway 从 GitHub 自动部署 `apps/api`。它有「Watch Paths」设置，决定**哪些文件的改动会触发重新构建**。

### 争议

**要不要在部署文档里写明这件事，并检查 Watch Paths 的当前设置？**

### 已确认的事实

**2026-10-05 真的发生了一次静默跳过：**

```
我 push 了一个提交，其中改了 Dockerfile、.dockerignore、pnpm-lock.yaml、
pnpm-workspace.yaml（为了修一个会阻断构建的问题）
      ↓
Railway：SKIPPED —「No changes to watched files」
      ↓
部署没有重建，而我改的正是【构建配置】
```

**后果**：我的修复**从未被构建验证过**。而更一般地——**只改构建配置的提交会被静默忽略，
部署悄悄落后于仓库，没有任何提示。**

（后来手动 Redeploy 验证了那次修复是对的。）

### 【我的判断】写

至少写明两件事：
1. **Watch Paths 必须包含 `Dockerfile` / `pnpm-lock.yaml` / `pnpm-workspace.yaml`**（或留空＝监视全部）
2. **改构建配置后要手动 Redeploy**，不能指望自动触发

### 【另一种合理做法】不写

- 这是一次性的设置问题，在 Railway 控制台点一下就完了，不需要文档
- 部署文档写太多运维细节会没人看
- 而且 **Watch Paths 的实际值我无法从仓库里读到**——它只存在于 Railway 控制台，
  写进文档就成了"文档描述一个仓库里看不见的状态"，**那正是会漂移的东西**

### 【判据】

**`apps/api` 的构建配置多久改一次？**

- **几乎不改** → 选「不写」。一次性的坑，踩过一次就知道了
- **会改**（调整依赖、改镜像、改构建步骤）→ 选「写」。
  因为**它的失败模式是静默的**——不写的话，下一个人（或下一个 AI）会再踩一次

**相关的旁证**：这个项目里所有伤人的问题都是**静默**的那类
（README 数字过期、孤儿定价条目、`/api/health` 假绿、这次部署静默跳过）。

**不落纸的话，下次就得重新想一遍。**

| # | 事项 | 状态与完成判据 |
|---|---|---|
| 1 | **重新部署后端到自有云服务器**（解决「线上站点半坏」） | **已决定，未开始**。判据：**线上点「登录」能走通全流程**（注册 → 登录 → 抽一次 → 刷新看历史还在）。在那之前，这一条一直挂着 |
| 2 | **`--dry-run-only`**：只跑干跑就停，不写盘、不快照、不枚举 | **已决定，未排期**。暂存功能不依赖它（用户明确说「保存不跑任何东西」），但独立有用：试阈值看 `hits`、调试手写表达式、判断一条规则够不够稀有——现在这些都要跑完 ~8 分钟枚举 |

### 第 1 条的决议摘要（详细分析见下方的原始记录）

```
决定   重新部署 API 到自有云服务器（2 核 2GB CentOS），数据库继续外置（Supabase）
       前端保留在 GitHub Pages，只更新 API_BASE_URL 后重新构建
具体   PM2（--max-memory-restart 512M）· Nginx 反代 · 2GB Swap · HTTPS
HTTPS  已确认可行：Let's Encrypt 的 shortlived 档支持 IP 标识，
       certbot 5.4+ 用 --preferred-profile shortlived --ip-address <IP>
       （不需要域名。代价：证书仅 ~6.7 天，必须自动续期）
```

**实施时要带上的坑**（都是实测踩过的，不是推测）：

```
dist/server.js 不存在         → 用 pnpm -C apps/api start（运行时靠 tsx，不编译成 JS）
tsx 大概率是 devDependency     → 建议走现有 Dockerfile（已在 Railway 构建成功过）
lockfile 与 workspace 对齐     → Dockerfile 里已处理
HUEDLE_TRUST_PROXY=1          → Nginx 后面同样需要，否则限流把所有人算成同一个
Swap 必须在起服务【之前】配      → 2GB 内存没有 Swap，OOM 会杀掉进程
API_BASE_URL 必须在构建前改     → 地址是烧进 bundle 的，改晚了前端还指旧地址
```

### 原始记录：线上站点现在是半坏的——怎么处理？

> ⚠️ **这份分析写于「决定重新部署」之前。**
> 其中【我的判断：改成纯本地模式】**已被取代**——后来的决定是**重新部署后端到自有云服务器**，
> 而不是放弃登录模式。
>
> **保留它是因为下面那些事实与判据仍然有效**：静默失败为什么最伤人、
> 「本地数据库 + 线上登录」这个组合为什么不存在、以及当初该用什么判据决定。
> **但不要把那一节的结论当成现在的方向。**

### 背景（读这一条所需的最小上下文）

**HueDle** 是每日随机颜色收集游戏，有两个模式：

- **本地模式**：数据在浏览器 `localStorage`，不需要后端
- **登录模式**：注册/登录、服务端保存每日结果与历史，**需要一个后端 API**

部署形态：

```
前端   GitHub Pages（https://zhFelix.github.io/HueDle/）—— 静态，免费
后端   Railway（https://huedleapi-production.up.railway.app）
数据库 Supabase（悉尼）
```

**关键机制**：前端的 API 地址在**构建时烧进 bundle**（`VITE_API_BASE` ← GitHub Actions 变量
`API_BASE_URL`）。所以地址一旦确定，就固定在那份产物里，**改不了**。

### 争议

**Railway 被停掉之后，线上站点该怎么办？**

### 已确认的事实

**2026-10-06，Railway 服务被停用。**此后：

| | 状态 |
|---|---|
| **本地开发**（`pnpm dev`） | ✅ **不受影响**。`VITE_API_BASE` 没设时 `lib/api.ts` 回落到 `http://localhost:3001` |
| **线上站点的本地模式** | ✅ 仍可用（数据在 localStorage） |
| **线上站点的登录模式** | ❌ **失效**——bundle 里烧死的地址已经死了 |

**所以线上站点现在是"半坏的"**：一个功能不工作，而页面不会告诉访问者"这是被主动关掉的"。
点「登录」会看到一个错误横幅。

### 【我的判断】改成纯本地模式，明确去掉登录入口

**理由不是"登录不好"，是"现在的状态会骗人"**。

这个项目里真正伤人的从来不是"功能没有"，而是**"看着像有"**：
README 写 126 条徽章、孤儿定价条目、`/api/health` 假绿灯、部署静默跳过——
每一次的代价都来自"它看起来是好的"。

**半坏的站点是同一类。**访客会以为站点坏了，而不是"这个功能被关掉了"。

### 【另一种合理做法】什么都不做

- **如果线上站点只有你自己看**，那你知道它为什么坏，不必为它改代码
- 重新部署 API 之后一切恢复，**改动就是白做的**
- 而且"改前端"意味着一次新的部署，而**部署本身现在也有静默失败的风险**

### 【判据】

**线上站点现在还有别人在看吗？**

- **只有你自己** → 选「不做」。你知道原因，改它是浪费
- **有别人（哪怕一个）** → 选「改」。因为**他无法知道你停了后端**，
  他只会得到一个"这站坏了"的印象，而且**不会告诉你**

**第二个角度**：你**多久之内会重新部署后端**？
- 很快（几天内）→ 先不做，那只是短暂状态
- 不确定 / 很久 → 那就得处理，否则"短暂"会变成"长期"

### 相关的结构性约束（讨论时要知道）

```
数据库搬到本地  →  API 也必须在本地（云上的 API 连不到你本机的库）
                →  线上站点【必然】只剩本地模式
```

**所以"本地数据库 + 线上登录"这个组合不存在。**要让线上有登录，
后端就得有一个**常驻可达**的地方（PaaS 或自己的机器 + 隧道）——那是一个单独的、更贵的决定。

## 下次往这里写什么

> ⚠️ **以下是判断，不是规则。**署名 agent、日期 2026-10-05。
> 依据只有当时那三个案例。**如果你按它筛掉了一个后来证明该写进来的问题，那就是它错了。**


**不是所有技术选择都该进这份文档。**判据是：

| 该进 | 不该进 |
|---|---|
| 有两种合理做法、各有代价，需要人拍板 | 只有一种做法，或另一种明显更差 |
| 结论依赖**项目之外的判断**（产品取向、使用频率预期） | 纯技术事实问题，查一下就有答案 |
| 错了的代价**不能立刻看出来**（它可能很久以后才显现） | 错了当场就红，改回来很便宜 |

**当时认为**第 3 条尤其值得留意，理由是——就当时见过的事故而言，**真正伤人的不是"写错了"，
而是"写错了但所有测试都是绿的"**：

```
README 写 126 条徽章（当时实际 128）          人工发现
pricing.gen.ts 留下孤儿条目 extreme-404       人工发现，只差一步被提交
最稀有徽章被显示成「1 / 1 = 必然抽中」          人工审设计文档时发现
```

**就那 4 次而言**，没有一次是被测试发现的。

（限定词是必要的：这是 4 个案例的统计，**不是一条规律**。）

**当时的推论**：所以进这份文档的，应该主要是**测试看不见的那类决定**。
